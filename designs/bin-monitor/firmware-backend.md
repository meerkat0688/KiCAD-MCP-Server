# 韌體與通知服務設計

本文件定義原型行為與介面；reference-model 只驗證離線偵測，不含可燒錄韌體或可部署後端。

## 偵測狀態

校正狀態 UNCALIBRATED / CALIBRATED，健康狀態 WARMUP / OK / SENSOR_FAULT，滿載鎖存 NORMAL / FULL，各自分開。通知另有 IDLE / PENDING / API_ACCEPTED / CANCELLED / NOTIFY_FAULT，不用一個 enum 覆蓋所有狀態。故障可以與已鎖存的滿載同時存在。

1. 驗證 H 有效，並確認新讀值的驅動 status、距離量程及時間戳；使用 5 秒固定節拍，每次只處理一個新量測。
2. 無效值立即重置 full_since 與 clear_since，依 DP-01 清中位數視窗；保持 full_latched 和 event_id。失去有效值 30 秒後進 SENSOR_FAULT，獨立 watchdog 呼叫也必須觸發，不依賴感測函式正常返回。
3. 累積 3 筆新有效值後取中位數 d；F=clamp((H-d)/H×100,0,100)。無效 status 不進此運算。
4. 未鎖存 FULL 且 F≥80，從首次符合的濾波值開始連續 60 秒，建立一個唯一事件，原子儲存事件及 FULL 鎖存後才交給傳送任務。F<80 或 invalid 重新計時。
5. 鎖存 FULL 且 F≤50，連續 120 秒後 NORMAL，原子保存清空及該事件取消資訊，才允許下一個事件。F>50 或 invalid 重置清空計時。
6. 50<F<80 保持原鎖存狀態；既有事件不因兩小時滿載再建立。斷電恢復不沿用失去的單調計時器。

初次暖機取樣在 t=0/5/10 秒，若全部滿載，首個濾波門檻在 t=10，事件最早 t=70。MSG-03 的 90 秒是從 t=10 起算，所以計時確認用掉 60 秒後，持久化、HTTPS、排程、LINE 與群組可見總共只有 **30 秒預算**。分配目標：裝置儲存與上傳 5 秒、後端排程與呼叫 5 秒、群組可見預留 20 秒；這是延遲預算，非已達標數字。不得因 5 分鐘背景重試而延誤健康連線的首次傳送。

## 校正及操作

本機診斷指令建議 `status`、`calibrate-empty`、`logs`。校正需由操作者確認空桶，取得 10 筆 status 正常讀值，檢查穩定性（初始提案 max-min≤20 mm）後保存中位數 H、感測設定版本、CRC、schema_version 與時間品質。若超出候選可驗證量程／不穩定則保持 UNCALIBRATED，不使用舊失敗校正值覆寫成功值。校正方法與重校時事件處置需在韌體實作時測試；有未完成 FULL 事件時先禁止任意重校，避免清除去重鎖存。

USB 診斷同時列出 height_state、sensor_health、network_state、notify_state、clock_quality。未同步時顯示「時間未確認」，以 boot_id + 單調序號保留順序。未驗證本機狀態燈，板上充電燈不可標示滿載。

## 持久化與容量

裝置使用原子更新或雙槽 CRC journal，保存 H、full_latched、當前 event_id、建立時間品質、待送事件、取消 tombstone、不可回退的事件序號。掉電注入點包含「建立但未送」「送出但回應丟失」「LINE 已接受但裝置未收到狀態」。網路傳送前必須先落盤，不以 Wi-Fi 重連建立新 event_id。

狀態／通知紀錄採有界環形儲存，原型先分配 512 KiB。以每筆 256 bytes、每天 200 筆狀態／通知事件估算，7 天為 358400 bytes，尚有餘量；這是容量假設，需測試異常暴增、回收與 flash 磨耗。相同故障合併計數，不能每 5 秒 append 一筆「仍斷線」而失去 7 天紀錄。真實 raw 測試資料存主機／後端：每 5 秒一筆，7 天有 120960 筆，不承諾全存在 4 MB flash。後端保存至少 7 天且備份，但斷網期間的本機紀錄仍需保留。

## 裝置至後端協定

HTTPS、驗證伺服器憑證；每裝置獨立認證，不放 LINE token。範例 JSON 見 event-example.json；只含示意 BIN-001，不含任何憑證、groupId、Wi-Fi 密碼或實際位置資料。

後端以 `(device_id,event_id)` 唯一鍵建立交易。每裝置有單調 revision；裝置復網先一次提交最新狀態、取消 tombstone 及待送事件，再排程通知，禁止先重播舊 FULL 再處理清空。過時 revision 不得覆蓋新狀態。群組收件者由後端已授權設定選定，裝置不能任意指定 groupId。

送出前檢查：未取消、未超過 24 小時、最新狀態非 fault、已完成 DP-03 新樣本確認、時鐘年齡可信。後端離線超過 15 秒（設計初值）沒有新鮮狀態則暫停送出；恢復後先核對裝置。已清空或過期事件永久取消，不因下次滿載重用。清空與正在進行的外部 API 呼叫存在不可撤回的競態；以同裝置序列鎖縮小窗口並記錄，不能宣稱全域 exactly-once 或能收回 LINE 已接受的訊息。

後端第一次 LINE 呼叫前就持久化 UUID retry_key 與不可變的訊息本文。每次呼叫沿用相同 recipient/body/key；補送的原時間與「延遲送達」於第一次嘗試前決定，若首次請求結果不明，不可同 key 修改訊息內容。[S09]

## LINE 與網路錯誤

官方帳號先啟用群組加入、由負責人加入測試群組，從驗證簽章的 webhook 取得並核准 groupId。[S10] 未配置時只做本機記錄，不能發出真實請求。

| 結果 | 行為 |
|---|---|
| 200 / 成功接受 | 標記 API_ACCEPTED；停止自動重送；人工群組可見證據另記 |
| 409 + 相同 retry key 已被接受證據 | 當作既有接受，記 accepted request ID；不再建立新 key |
| 連線 timeout / 5xx | 5、15、60 秒後重試，之後每 5 分鐘，受 24 小時事件期限限制；小幅 jitter 不侵占首次／復網時效預算 |
| 400/401/403 等請求或權限錯誤 | NOTIFY_FAULT，待配置修復；避免無限快速重送 |
| 429 | 分辨月額度不足與速率限制；額度不足停送並顯示異常；速率限制依官方限制延後且受期限限制，不套用快速重試 |

LINE retry key 自首次請求起有效 24 小時；專案另以「事件年齡超過 24 小時」取消，兩個時鐘不得混淆。保留 HTTP code、request ID、accepted ID 與遮蔽後原因，不記 Authorization header。API 接受不等於群組可見。[S09]

群組訊息用量依收件人數計算；帳號方案與每月成本待選定，不宣稱免費或費用已通過。訊息內容必須標示「高度估計，非容積」。[S11]
